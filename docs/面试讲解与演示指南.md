# TermGuard 面试讲解与演示指南

> 配套 README 使用：README 讲"是什么"，本文档讲"面试怎么讲、怎么演示"。

## 一、开场话术（按时间预算选择）

### 30 秒版（电梯版）
"我做了一个面向游戏本地化的术语一致性智能质检工具。译员最痛的两个点——**术语上下文不一致**和**特定语境校验难**——我用'规则引擎 + 大模型复核'两层来解决：规则层抓占位符、数字、术语这类确定性错误，快且可解释；大模型层抓语境、语域这类语义问题，可选接入、无 Key 自动降级。内置 26 句游戏文案 Demo，埋了 14 处典型错误，检测结果零漏报、零误报。"

### 1 分钟版（自我介绍用）
"这个项目的选题来自对本地化 QA 流程的调研：译员和 QA 花大量时间人工核对术语一致性、占位符、数字这些重复劳动，而且'同一个词在不同上下文译法不同'（比如 Level 在角色语境是'等级'、在关卡语境是'第 3 章'）靠人眼很难查全。
工具的设计思路是分两层：**规则层**用 Python 实现占位符/数字比对、术语库驱动的精确匹配和跨行一致性检测——这类问题确定性强，用规则最合适，免费、可解释、没有幻觉；**LLM 层**可选接入 DeepSeek，用结构化输出做语境和语域复核——这类问题才需要语义理解。
技术上复用了我之前 RAG 项目的经验：Python 生态、结构化输出、降级策略；前端用 Vue3 + ECharts 做了完整的可视化界面，术语库支持在线编辑，质检结果支持一键忽略形成反馈闭环。整个后端加前端单端口部署，双击即用。"

## 二、演示操作流程（逐屏脚本）

> 演示前确认：服务已启动（start.bat），浏览器打开 http://127.0.0.1:8010

### 第 0 步：空状态（5 秒）
- 动作：停在初始页
- 讲："这是一个给本地化 QA 用的工作台，左侧配置数据和术语库，右侧出质检报告。注意它**不是翻译器**——它解决的是译员交付后、人工审核太慢太漏的问题。"

### 第 1 步：载入内置 Demo 并启动质检（15 秒）
- 动作：左侧「① 待检文本」默认选中"内置示例"→ 点击底部「▶ 开始质检 · 26 句」
- 讲："内置了一份游戏本地化的双语文案，26 句里故意埋了 14 处常见错误——术语误译、跨行不一致、占位符丢失、数字被改、漏译等等。这份数据是我自己造的，就是为了能稳定演示。"

### 第 2 步：结果总览（20 秒）
- 动作：指向顶部统计卡 → 仪表盘 → 环形图
- 讲："通过率 46%（12 句干净/26 句）——注意这是演示数据，故意做脏的，真实场景通过率会高得多。
  左边仪表盘是无问题句占比；环形图把问题按类型归类：术语 7 处、数字 4 处、占位符 2 处……
  **设计原则：规则抓确定性问题，所以报告可解释、可分类、可一键修复，而不是丢给模型一句'你看哪里不对'。"**

### 第 3 步：经典 Case 讲解（挑 2-3 个，每个 20 秒）
**Case A · 术语跨行不一致（第 2 行）**
- 讲："第 2 行把 Cloud Sync 译成了'云备份'，但第 3 行用的是标准译法'云同步'。工具报了两个问题：术语违规 + **跨行不一致**——它统计了全文，发现同一个词条在其他行是译对的，专门提示'第 3 行使用标准译法，本行未遵循'。这正是 JD 里说的'术语上下文不一致'痛点，人工在 100 页文档里根本翻不完。"

**Case B · 上下文限定词条（第 17 行）**
- 动作：点开「② 术语库」区域的"编辑"，找到 Level / Level 3 两条
- 讲："这是我认为最有业务价值的一点：同一个词在不同语境译法不同。术语库里 Level→等级（角色语境），Level 3→第 3 章（关卡语境）。第 17 行'Quest marker: Level 3'是章节标题语境，却译成'等级 3'——工具用**长词条优先匹配**识别出这里命中上下文限定词条，报错。第 4、23 行的 Level 10/Level 5 是角色等级，译'等级'就完全正确，没有误报。"
- 反问钩子："这对应本地化行业里的 context-scoped terminology 做法，术语库规范里叫 scope。"

**Case C · 占位符（第 8 行）**
- 讲："游戏文案大量依赖运行时参数：第 8 行源文是'Press [E]'，译文把 [E] 弄丢了——游戏里按键提示就会消失。占位符这类错误用**正则精确比对**，两边集合一对比就抓出来了，零成本、百分之百确定。"

### 第 4 步：术语库编辑 + 反馈闭环（15 秒）
- 动作：随便改一条术语 → 保存 → 重新质检；对某条问题点"忽略"
- 讲："术语库支持在线增删改，还支持'保留英文'开关——专有名词（GvG、首领名）不允许意译。结果页每条问题可以'忽略/恢复'，这就是把 QA 的裁决沉淀下来的入口，为后续做反馈闭环迭代留了接口。"

### 第 5 步（可选）：自定义数据
- 动作：切到「粘贴/上传」→ 粘贴几条自己写的双语 → 载入 → 质检
- 讲："工具不绑死 Demo，粘贴或上传 CSV/TXT 就能检自己的文本，术语库也可以完全自定义——换一批术语就是另一个产品的本地化项目。"

### 第 6 步（可选 · 加分项）：AI 语境复核
- 动作：开启「③ AI 语境复核」→ 输入 DeepSeek Key → 重新质检 → 指向多出来的"AI 复核"条目
- 讲："规则层处理不了的语义问题——语域不统一、误译、信息遗漏——可以交给大模型复核，结果用 JSON 结构化输出回填到同一张报告里。**没配 Key 时系统自动降级为纯规则检查，演示永远不翻车**，这个降级设计我在之前的 agent-report 项目里也用过。"

## 三、技术点"面试怎么讲"（每个配一句钩子）

### 3.1 为什么不用纯 LLM 一把梭？—— 分层设计
> "确定性问题用规则、语义问题才用 LLM，是我刻意做的架构决策。占位符丢没丢、数字对不对，LLM 可能给出不稳定的答案还费钱；反过来'语域是否统一'规则永远做不了。**用最合适的工具解决当前问题**——这本身就是岗位要的实用主义。而且规则层的错误报告可解释、可分类，QA 能直接照着修。"

### 3.2 上下文限定词条怎么实现的？—— 长词条优先 + 区间去重
> "术语按 source 长度降序排序，在源文里做子串匹配并记录命中区间；后匹配的短词条如果和已命中区间重叠就跳过。这样'Level 3'命中后，'Level' 就不会再在这段里重复报错——同一个词在不同上下文由**更长、更具体的词条**接管，这就是 context-scoped terminology。"

### 3.3 跨行不一致怎么检测？
> "扫描全文时给每个词条记录命中行和该行是否合规，最后汇总：同一个词条在多行出现、部分行对部分行错时，给错误行补一条'术语不一致'提示，并列出正确行号。对应 QA 的'全文一致性'检查，传统上只能靠人肉翻阅或术语库工具事后导出。"

### 3.4 占位符/数字比对原理？
> "正则把 {player}、%s、[E]、数字（含 10% 这种带百分号的）提取成集合，比较两边**多重集差集**——源文有译文没有 = 丢失（高危），译文多出来 = 可疑（提醒）。数字规则会放过 404 这种两边一致的场景，避免误报（Demo 第 20 行专门验证了这点）。"

### 3.5 漏译检测怎么做才不误报？
> "中文比英文紧凑，直接按字符数比会大量误报（我最初用 40 字符阈值，2 处误报）。调成**长句（≥70 字符）且译文 < 源文 30%** 才触发，验证后零误报。这个调参过程本身就能讲：我在 tests/selftest.py 里维护了一个含标注的评估集，每次改规则跑一遍漏报/误报——**用数据而不是拍脑袋调规则**。"

### 3.6 LLM 层怎么接的？—— OpenAI 兼容 + 结构化输出 + 降级
> "用 openai SDK 走兼容协议调 DeepSeek：temperature 0.1 压低随机性、10 句一批控制 token、system prompt 里给它术语库和双语 JSON、要求只输出 JSON 数组（{line, type, reason, suggestion}），返回后解析合并进统一报告。**没 Key 返回空并提示降级**，前端文案明确告知'仅规则检查'，不会让用户误以为 AI 参与了。"

### 3.7 怎么验证引擎质量？—— 评估集
> "tests/selftest.py：26 句 Demo 里 14 行是标注过的'应该有问题的行'，脚本断言漏报=0、误报=0。面试官如果问准确率，可以答：规则层在评估集上零漏报零误报；规则的本质是精确匹配，它的'准确率'由词条质量和正则覆盖率决定，而语义层才需要统计指标——这也是分层的好处，指标含义清晰。"

### 3.8 前端为什么值得做？—— 面向非技术用户
> "工具的最终用户是译员和 QA，不是程序员，所以交互和可读性就是产品力：Vue3 实现，ECharts 做通过率仪表盘和问题类型分布，每条问题展示'行号 + 类型徽章 + 源文/译文对照 + 修复建议'，高危/提醒分级用颜色区分，术语库抽屉式编辑。**把技术结果翻译成业务人员能看懂的报告，这本身就是'翻译需求'能力的体现**——对应岗位 JD 里'用通俗易懂的语言向非技术人员解释技术逻辑'。"

### 3.9 部署为什么单端口？
> "FastAPI 挂载前端构建产物，一个 Python 进程同时服务 API 和页面，双击 start.bat 就能用——本地化团队的 QA 工具要的就是低门槛。参考了我 agent-report 项目里 Docker 一键部署的思路，但这个工具面向个人/小团队，轻量优先。"

### 3.10 和简历项目的关联（主动讲，体现方法论复用）
> "RAG 项目我学会了'文档→切块→向量检索→生成'的管道思维和降级设计；agent-report 让我掌握了 LangGraph 编排、SSE 流式、结构化输出。TermGuard 是这些能力的**业务化落地**：同样是把痛点拆成管道（数据→预处理→检查→报告），但这次从'通用工具'变成了'行业工具'——说明我能把技术迁移到具体业务场景，这正是岗位要的'桥梁'角色。"

### 3.11 未来迭代方向（体现思考深度）
> "① **反馈闭环**：译员忽略/确认的结果回流，自动沉淀成词条或校准 prompt；② 支持 **TMX/XLIFF/SRT** 等行业格式直接导入，而不是 CSV；③ 加**术语提取**模块，从源文自动提候选词条；④ 规则层支持**多语言对**（中英只是起点）；⑤ 对接主流 CAT 工具导出结果。这些优先级我排了序：先做格式支持，因为真实项目第一步就是数据打通。"

## 四、可能被刁难的问题 & 应对

**Q：规则匹配会不会误报？比如译文用词序不同、同义词？**
> "会，所以规则层只做**确定性强**的判断：占位符、数字、词条是否出现，不做同义词判断——同义词是语义问题，交给 LLM 层。误报的处理：每行可'忽略'形成反馈，评估集持续回归。我宁愿规则少报但报的都对，语义类留给模型。"

**Q：这和 Trados/主流 CAT 工具的 QA 模块有什么区别？**
> "Trados 的 QA 偏格式与术语表比对，且术语库配置重、封闭生态。我的定位是**AI 时代的轻量质检**：一是上下文限定词条 + 跨行不一致是很多工具的盲区；二是把 LLM 语义复核和规则检查放进同一份报告，是新一代做法；三是从数据到结果全流程可控、可二次开发——对 AI 产品助理这个岗位，自己写的引擎比采购工具更能说明动手能力。"

**Q：你的 Demo 数据是自己造的，真实数据效果如何保证？**
> "Demo 是为了稳定演示和评估。真实场景我会：先用客户术语库和一批历史 QA 记录做评估集，跑出漏报/误报再调词条和阈值；工具支持上传真实双语文本，接口是通用的。这也是我为什么把评估集脚本作为项目的一部分。"

**Q：为什么不用现成的语言检查库（如 language-tool）？**
> "因为 80% 的检查项（术语、占位符、数字、一致性）是**项目特有规则**，现成库覆盖不了游戏本地化的业务语义，而且我需要对每条规则有完全的控制权来适配客户术语规范。语言拼写类错误未来可以作为补充层接进来。"

**Q：LLM 复核的成本和幻觉怎么控制？**
> "成本：LLM 层是可选开关，默认关；且只让它复核语义问题而不是重做规则层，10 句一批控制 token。幻觉：只输出 JSON、temperature 0.1、system prompt 明确'宁可少报不要误报'；规则层结果不经过 LLM，保证核心报告确定性。核心是**分层**——LLM 出错最多丢一条'AI 复核'提示，不影响规则结论。"

## 五、演示时间盒（如果面试官只给 10 分钟）

| 时间 | 内容 |
|---|---|
| 0:00-0:30 | 一句话定位：轻量、分层、游戏本地化 QA |

| 1:30-3:30 | 三个 Case：跨行不一致 / 上下文词条 / 占位符（打开术语库佐证） |
| 3:30-4:30 | 术语库编辑 + 忽略 = 反馈闭环 |
| 4:30-5:30 | （有 Key 时）开 AI 复核对比 |
