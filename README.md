# TermGuard — 本地化文本术语一致性质检工具

面向游戏本地化场景的自动化 QA 工具：对源文与译文逐句做确定性检查（术语、占位符、数字、漏译、跨行一致性），
并可选用大模型补充语义层复核（语境、语域、误译）。核心思路是**确定性规则优先、语义判断兜底**，
在保证零误报的前提下降低人工逐句核对成本。

- **技术栈**：Python · FastAPI · Pydantic · Vue3 · Vite · ECharts · DeepSeek（OpenAI 兼容接口）
- **运行方式**：单端口部署（FastAPI 同时托管前端静态资源）/ 前后端分离开发模式
- **当前状态**：规则引擎已覆盖 7 类常见问题，内置样本自测零漏报、零误报

## 解决的问题

本地化 QA 中最耗人力的几类问题，以及对应的处理方式与责任层：

| 问题 | 处理方式 | 责任层 |
|---|---|---|
| 术语译法不统一（同词不同译、跨文件不一致） | 术语库驱动的全量扫描 + 跨行不一致提示 | 规则层 |
| 术语存在语境差异（如 `Level` → 等级，`Level 3` → 第 3 章） | 上下文限定词条，长词条优先匹配 | 规则层 |
| 占位符/数字被改动或丢失（`{player}`、`[E]`、伤害数值） | 正则精确比对，零成本、高确定性 | 规则层 |
| 漏译、空译文、长句截断 | 长度与空值规则校验 | 规则层 |
| 语域不当、误译、信息遗漏 | 大模型语义复核（可选，分批结构化输出） | 语义层 |

## 架构

```
前端 Vue3（构建产物由 FastAPI 托管，单端口 8010）
  │  POST /api/check
  ▼
后端 FastAPI
  ├─ 规则层  checkers/rules.py      快、确定性强、可解释
  └─ 语义层  checkers/llm_check.py  慢、覆盖语义问题，无 Key 自动降级
数据层：backend/data/glossary.json（术语库）、check_history.json（检查历史）
```

**分层原则**：能用规则判定的绝不交给模型。占位符、数字、术语一致性这类问题有唯一正确答案，
用规则既免费又可解释；只有"这句话译得好不好"这类判断才交给大模型。

## 检测能力

内置一份游戏本地化样例：**26 句文案、植入 14 处典型错误、覆盖 7 类问题、术语库 12 条**。

| 类别 | 示例 |
|---|---|
| 术语误译 | `HP` → 健康点、`Cooldown` → CD |
| 术语跨行不一致 | `Cloud Sync`、`Quest` 在不同行译法不同 |
| 上下文限定词条误用 | `Level 3` 译为「等级 3」（应为「第 3 章」） |
| 专有名词被意译 | `GvG`、`Legionnaire's Blade` |
| 占位符丢失 | `{player}`、`[E]` |
| 数字改写 | `50` → `5000`、`10%` → `100%` |
| 空译文 / 未翻译 / 长句截断 | 长度与空值校验 |

**自测**：`tests/selftest.py` 对内置样本执行全量检查，比对期望结果与实际结果，输出漏报/误报清单。
当前结果：**零漏报、零误报**。

## 快速开始

### 环境要求

- Python 3.10+
- Node.js 18+（仅在需要重新构建前端时使用）

### 启动

```bash
# 1. 后端依赖
cd backend
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 2. 前端构建（前端代码有改动时才需要，仓库已包含构建产物）
cd ../frontend
npm install
npm run build

# 3. 启动（http://127.0.0.1:8010）
cd ../backend
.venv\Scripts\python main.py
```

Windows 下也可直接双击 `start.bat`（自动启动并打开浏览器）。

**开发模式**：后端执行 `python main.py`（:8010），前端执行 `npm run dev`（:5173，`/api` 已代理至 8010）。

### 自测

```bash
cd backend
.venv\Scripts\python ../tests/selftest.py
```

## 语义复核（可选）

界面左侧「AI 语境复核」开启后填写：

| 配置项 | 说明 |
|---|---|
| API Key | 仅保存在浏览器本地，不写入文件、不上传 |
| Base URL | 任一 OpenAI 兼容接口地址，默认 `https://api.deepseek.com` |
| 模型 | 默认 `deepseek-chat` |
| 批次大小 | 默认 10 句/批，温度 0.1，要求 JSON 结构化输出 |

不填写 Key 时自动降级为纯规则检查，内置样本的全部问题仍可检出。

## 设计取舍

| 决策点 | 采用方案 | 放弃的方案 | 原因 |
|---|---|---|---|
| 检查主链路 | 规则层优先，语义层可选 | 全部交给大模型 | 确定性问题的答案唯一，用模型既慢又不稳定；规则层保证零误报与可解释 |
| 术语匹配 | 长词条优先 + 区间去重 | 简单字符串替换 | 避免短词条先命中导致长词条失效，避免同一区间重复报错 |
| 词条语境 | 上下文限定词条（带前置条件） | 全局唯一映射 | 同一术语在不同语境下译法不同（`Level` / `Level 3`），单一映射必然误报 |
| 模型输出 | JSON 结构化 + 固定字段 | 自由文本解析 | 保证结果可渲染、可统计，便于后续比对与留档 |
| 无 Key 场景 | 规则层兜底 | 直接禁用功能 | 工具的核心价值不依赖模型，保证离线可用 |
| 部署 | 单端口（FastAPI 托管前端） | 前后端分离部署 | 内部工具场景下降低部署与分发成本 |

## 已知限制

- 术语库需人工维护与扩充，当前未实现术语自动抽取
- 语义层结果受模型影响，同一句多次调用可能产生细微差异，因此默认关闭、需人工开启
- 未做项目级与多语言隔离，当前为单术语库、单项目使用
- 批量导入以 CSV 为主，未适配主流本地化平台的工程文件格式
- 界面未适配移动端
